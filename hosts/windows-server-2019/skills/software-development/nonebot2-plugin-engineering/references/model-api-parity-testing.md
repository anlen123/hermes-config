# 让本地集成与参照实现的结果对齐（第三方判断 / 评分接口）

接一个「给分」类接口时，用户手里通常有个**参照实现**（网页控制台 / Playground、官方 quickstart 样例）。
他觉得「机器人结果不对」，九成不是链路断了，而是两边发出去的 payload 形态不同。
这份文件是把它对齐的固定打法。

## 先分清三种「不对」

| 现象 | 判据 | 处理 |
| --- | --- | --- |
| 链路断了（数据没进去） | 出站请求体里看不到用户输入的内容 | 修真链路，见 SKILL.md 的截获桩打法 |
| 输入相同、两边数字仍不同 | 请求体逐字一致但分数差十几点 | **payload 形态问题**，就是本文件 |
| 输入是不同的问题 | 两边问句本身不一样（换了个说法 / 换了个对象） | 先把问句统一再比，否则比出来的差值没有意义 |

最常见的误判：拿「用户控制台问 A」和「机器人问 B」两次结果直接比。**先确认两次问的是同一句。**

## 参照 payload 从哪来

- 网页控制台的分享链接**抓不到**（要浏览器登录态，curl 拿到的是拦截页）。别在这上面耗时间，
  直接要用户截图：控制台的 State / Questions 面板会把字段名、类型、值原样展示出来，够用。
- 官方文档的 quickstart 给的是权威字段表（`curl` 文档站的 `.md` 入口拿干净 Markdown）。
- **两者不一致时以官方 quickstart / 接口参考为准。** 控制台的 State 面板是 **JSON 编辑器**，会把输入
  包成 `{"state": "…"}` 再发出去 —— 那是编辑器形态，不是接口要求。用户 2026-09-29 拍板「包一个对象
  是错的」，最终用**纯字符串**。别再照控制台包对象：这条弯路已经走过一次（改完随即被否）。

## 受控 A/B：一次只换一个要素，每个变体跑 3 次

单次采样在判断/评分类模型上会抖 ±5~10 点，**一次的结果不能当结论**。正确姿势：

1. 固定输入（同一 state、同一问题），把 payload 拆成待验的要素（本例：`state` 是字符串还是对象、
   有没有带空值的可选字段）。
2. 做**隔离矩阵**：全组合各跑 3 次，看哪个要素真的驱动了差异。
3. 用真接口跑，别用猜。表格贴给用户。

### 实测（同一句中文 state、同一个问题，各 3 次）

| 变体 | 结果 | 结论 |
| --- | --- | --- |
| `state` 是对象 + 空可选字段（= 控制台形态） | 13% / 10% / 10% | 与控制台显示的 10% 一致 |
| `state` 是字符串 + 不带可选字段 | 23% / 23% / 27% | 参考实现如果是对象形态，这里就系统性偏高 |
| `state` 是对象 + 不带可选字段 | 8% / 11% / 9% | 与第一行同档 |
| `state` 是字符串 + 空可选字段 | 20% / 30% / 25% | 与第二行同档 |

结论：**驱动差异的是 `state` 的形态（字符串 vs 对象），可选字段无关。** 两种形态文档都算合法，
但形态会系统性改变给分（本例约 14 点）。这组数据留着当解释用：用户以后拿控制台（对象口径）的数字
来对账、说「机器人结果不一样」时，先用它说明差异来源 —— **结论是解释，不是改代码**，
口径已定为官方 quickstart 的纯字符串。

## 改完怎么证明「对齐了」

- 用**插件的真链路**再跑 3 次（真事件 → 适配器 → 规则 → handler → 真接口），看分数落到参照值附近，
  不要只跑一遍手写 curl 就算数。
- 报告用三列表：`参照值 / 改前 / 改后`，并交代副作用：
  * 老路径（不带引用的那种用法）分数也会跟着变几个点，因为 `state` 形态是全局统一的；
  * 请求体多出几十个输入 token。
- 把「怎么回退」写清楚（形态包装做成一行函数，回退就是改那一行），用户才敢拍板。

## 模型口味 ≠ 链路错误（要分开讲）

同一个 state、同一件事，**问句措辞**就能让分数在 13% ~ 84% 之间跳（「叫 X」/「名号是 X」/「现在还是叫 X」）；
判断类模型还会拿真实世界知识压过你给的 `state`。可以给用户的旋钮（都要他拍板）：

- 在问题里加「只依据上文内容判断」——实测把「按上文应为真」的例子从 46% 抬到 91%。
- 用 noul 的 `criteria`（true/false 各写一句「上文支持 / 上文不支持」）——同例到 93%，反问句压到 3%。
- 保持问句措辞稳定（同一件事换说法，结果不可复现）。

## 接口事实（本仓库在用的那个判断接口）

- `POST https://api.typesafe.ai/v1/systemone`，`Authorization: Bearer <key>`，`Content-Type: application/json`。
- body：`state`（文本或 JSON 对象）+ `model`（`jev-latest`）+ `questions`（键名自定，不发给模型）。
  一条问题：`{"<键名>": {"type": "noul", "instructions": "<陈述句或疑问句都可>"}}`；
  `instructions` 可带可选 `criteria`。
- 应答给出该问题的 `true` 概率；卡片页脚记 `jev-<版本> · <输入>+<输出> tokens`，可当「同一份 payload」的指纹。
- 只吃文本：图片/音频/视频不支持，图片段塞进去不生效。

## 顺手要做的两件事（用户会要）

1. **把每次出站请求体写进日志**：发请求前记一行单行 JSON（`json.dumps(payload, ensure_ascii=False)`），
   并对 api key 做一次兜底替换（key 万一被写进 `state`）。用户之后自己 `grep "\[<插件\] 请求" bot.log` 就能核对。
2. **给出站请求体做「用量指纹」自证**：同内容再真打一次，比对 usage 数字与卡片/日志记下的是否一致，
   一致即同一份 payload，可直接排除「中间把字丢了」。
